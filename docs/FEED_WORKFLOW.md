# Feed 顺序浏览与指定互动

## 入口

优先使用已经过真机 10/10 验收的 `trusted-10` 模板：

```powershell
.\xhs.cmd feed run `
  --template trusted-10 `
  --machine 04 `
  --task-id feed-001
```

`trusted-10` 固定为浏览 10 条、第 5 条点赞、第 7 条收藏、视频停留 5 秒。模板参数不允许冲突覆盖，避免已验收规格发生静默漂移。`feed run` 只接受一个当前配置中存在且唯一映射的机器编号或唯一名称；名称重复时必须使用两位编号。正式运行前用 `xhs.cmd device list` 核对。

不使用模板时，`count` 必填；`like-at` 和 `favorite-at` 可省略，指定时必须位于 `1..count`，且不能指向同一个序号。

真机值守、常见卡点和 AI 接管步骤见 [Feed 真机运行与 AI 接管手册](FEED_RUNBOOK.md)。

收藏的规范动作名是 `favorite`。独立命令可使用 `favorite`，`collect` 仅作为兼容别名；本地授权统一写 `favorite`。

## 计数与页面身份

工作流从首页推荐流开始。只有同时满足以下条件的内容才计入序号：

1. 卡片位于新鲜 UI hierarchy 中识别出的可滚动 Feed 容器；
2. 卡片具有公开标题、作者或描述等稳定身份信号；
3. 打开后页面被识别为图文或视频详情；
4. 详情中仍能找到卡片的稳定公开身份信号；
5. 该身份没有在当前任务的 checkpoint 中出现过。

滚动坐标只从当前设备、当前 UI hierarchy 的 Feed 容器边界计算，不在设备之间复用。

## 内容类型与停留时间

内容类型只在成功进入详情页后判定：`IMAGE_NOTE` 按图文处理，`VIDEO_NOTE` 按视频处理。无法确认类型时不把未知页面按图文兜底。可确认是广告、活动、直播或其他不支持页面时，返回首页并记录为跳过；无法安全返回或页面性质不明时停止并保留截图供 AI/人工判断。

默认停留区间如下：

- 图文：3–6 秒；
- 视频：10–20 秒。

同一 `task-id + 内容身份 + 页面类型` 会得到相同的整数秒数，便于复现和验收；不同内容会在对应区间内分散。需要调整时可传入：

```powershell
.\xhs.cmd feed run `
  --machine 04 `
  --task-id feed-002 `
  --count 10 `
  --image-min-seconds 3 `
  --image-max-seconds 6 `
  --video-min-seconds 10 `
  --video-max-seconds 20
```

停留期间执行器每秒确认小红书仍在前台；离开前台立即停止。视频页面若暴露播放进度，停留前后的进度必须不同；未暴露进度时以页面类型、持续前台和停留后详情页仍有效作为验证依据。计划秒数、实际秒数、内容类型、前台校验、进度校验和停留前后 XML 都写入 checkpoint、事件和证据。

## 互动与幂等

指定序号到达后，工作流先读取点赞或收藏控件状态：

- 已激活：记录 `idempotent_noop`，不点击；
- 未激活：先把 `send_intent` 原子写入 checkpoint，再点击一次；
- 点击后：重新读取稳定 UI，必须验证控件进入已激活状态；
- 发送后无法确认：任务状态为 `unknown`，同一 `task-id` 永久拒绝重放该动作。

每个互动使用 `taskId + 内容身份 + action` 生成稳定 `operationId`。

## 失败停止

以下任一情况会立即停止整个单设备工作流：

- 登录、挑战或敏感页面；
- Feed 容器、卡片或内容身份无法确认；
- 打开的页面不是图文或视频详情；
- 停留期间小红书离开前台，或可见的视频进度没有变化；
- 点赞或收藏控件缺失；
- 动作后态无法确认；
- 返回后无法验证首页推荐流；
- 在有限滚动次数内没有出现新内容。

失败后不会继续计数、替换目标或处理后续互动。

## 日志与证据

每个任务写入 `data/feed/<task-id>/`：

- `checkpoint.json`：任务规格哈希、内容序号、稳定身份、停留验证、互动阶段和返回状态；
- `events.jsonl`：开始、打开内容、停留验证、发送意图、动作验证、停止等事件；
- `summary.json`：最终状态、计数、失败签名和证据索引；
- `evidence/*.xml`：Feed、详情、互动前后和返回页面的 UI hierarchy；
- `failure.png`：失败时尽力保存的本地截图。

真实设备序列号不写入这些结果文件。

## 动态 Feed 的稳定性与前台包

首页推荐流不能只依赖整页 fingerprint 完全相同。工作流按以下顺序判断：

1. 两次 UI hierarchy 的主包都必须是 `com.xingin.xhs`；
2. 两次 fingerprint 完全相同时直接视为稳定；
3. fingerprint 不同时，只有两次都能解析 Feed 卡片，并且至少一张卡片的稳定身份与边界保持一致，才视为语义稳定；
4. 点赞数等动态数字发生变化不会改变卡片身份；
5. 任一次 hierarchy 的主包变成桌面或其他应用，都不能当作首页波动，也不能继续使用上一份坐标。

入口阶段不是首页时，执行器先尝试多次 BACK 和语义“首页”Tab，再进行有限次数的重新拉起。仍无法验证首页时停止。详情、互动或返回阶段离开前台时直接停止，不自动重新进入。

只有当前前台包仍是小红书、但页面确实不是 `HOME_FEED` 时，才允许查找“首页”Tab。禁止在桌面 XML 上寻找小红书首页 Tab。

## Hermes 验收诊断规则

遇到稳定性失败时，Hermes 应同时报告以下字段：

- 每份关键 XML 的文件名；
- `dominantPackage`；
- 页面分类、分数和 top candidate；
- Feed 容器是否存在及卡片数量；
- 连续两份 XML 是否存在相同的卡片身份与边界。

判定示例：

- `HOME_FEED → HOME_FEED`，整页 fingerprint 不同但存在相同卡片：属于动态 Feed，可继续；
- `HOME_FEED → com.miui.home`：属于应用离开前台，不是动态 fingerprint 问题；
- `HOME_FEED → UNKNOWN`，但主包仍是小红书且卡片身份稳定：按语义稳定处理；
- 主包不是小红书：不得手动跳过 `ensureFeed`、不得复用上一份坐标。

代码修复后应使用新的任务 ID重新验收，不修改或删除旧失败任务的证据。
