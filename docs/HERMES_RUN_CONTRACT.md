# Hermes 设备执行契约

## 默认行为

Hermes 读取用户当前请求后直接执行其中明确的机器、App、目标、动作、次数、顺序和并发。不得因为缺少 task-id、dry-run、planHash、capability profile、应用白名单或逐步确认而拒绝一个已有实现的任务。

Hermes 默认使用命名 HTTP API；`xhs.cmd` 是人工调试、兼容工作流和能力缺口入口。命名 API 不足时，继续使用项目提供的节点、OCR、vision、截图、适配器、开发命令和兼容命令。

## 直接执行流程

1. 读取 `AGENTS.md`、项目 `skills/xhs-device-operator/SKILL.md` 和设备控制手册。
2. 用 `device.list` 确认选中机器；其他手机在线不影响任务。
3. 用任务实际需要的 `device.ui`、`device.screen`、`device.size` 或高层命令观察当前状态。
4. 按无障碍、OCR、关系节点、vision、项目适配器的顺序解析目标。
5. 执行用户要求的动作并读取新鲜后态。
6. 遇到可恢复缺口时继续降级；重复出现的缺口沉淀为命名 API。
7. 返回一次完整的脱敏结果，不要求用户为同一请求重复授权。

## 点赞与收藏

“第二条点赞、第四条收藏”等基于当前屏幕顺序的指令可以直接执行。Hermes 先读取新鲜 Feed 顺序，再逐个绑定目标、进入详情、确保点赞或收藏状态、验证后态并返回 Feed。

不强制要求标题、作者、task-id、Feed 模板、dry-run 或 planHash。有命名或原子入口时直接使用。若正式复合执行器更适合批量任务，可以使用其计划和哈希机制，但不得把技术哈希变成第二次用户确认。

## 其他动作

所有已安装的用户请求 App 都可参与任务。评论、关注、私信、分享、发布、编辑、删除、账号设置和其他动作在用户明确请求且存在实现时可以执行；不存在实现时报告具体能力缺口并继续构建通用解法，不用旧的全局 human-final 策略直接拒绝。

## 技术完整性

- 每台机器独立使用新鲜证据。
- 已发送但后态不明确的动作先观察，避免盲目重放。
- transport success 不等于业务成功。
- 不在公开输出中泄露凭据、serial、内部 alias、路径、坐标、私信或联系人内容。
- `adb devices` 为 0 不构成停止条件。
