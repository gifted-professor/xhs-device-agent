# 小红书设备控制能力地图

> **编辑必读**：本文件是项目能力边界的唯一总地图。修改前请先阅读 [编辑规则](#编辑规则)。任何状态变更必须有真实操作验证或明确的业务边界决策支撑，禁止凭猜测覆盖已有记录。

本文件记录 xhs-device-agent 项目在小红书设备控制方向上的能力边界与探索进度。状态图标必须明确，禁止使用 `[x]`/`[ ]` 等歧义标记。

## 状态图例

| 图标 | 含义 |
| --- | --- |
| ✅ | 已验证：通过真实 HTTP 或回归测试验证可用 |
| 🔄 | 部分验证：有临时绕行或 live 验收，但缺少通用修复 / 回归测试 |
| ❓ | 待验证：方向已识别，尚未验证 |
| ⛔ | 明确不做：业务或技术边界决定不实现 |
| 🚫 | 暂不做：当前阶段不做，未来可能开启 |

## 编辑规则

1. **状态图标必须统一**：只使用 ✅ / 🔄 / ❓ / ⛔ / 🚫，禁止使用 `[x]`/`[ ]` 或任何其他歧义标记。
2. **已验证能力降级必须说明原因**：将 ✅ 改为 🔄/❓/⛔/🚫 时，必须引用 `config/device-control-incidents.json` 中的 incident ID，并写明降级原因和日期。
3. **新增能力按模块归类**：不要在没有共识的情况下创建新模块。如果现有模块无法容纳，先与维护者确认后再新增。
4. **修改他人已验证条目必须留痕**：在说明末尾追加 `// 修改人 + 时间 + 原因` 格式的注释。
5. **能力描述必须包含**：已验证入口、未验证入口、限制条件。不能只写“已验证”三个字。
6. **状态互转必须有依据**：
   - 从 ❓ 改为 ✅ 或 🔄：必须有真实设备操作验证
   - 从 ✅ 改为 🔄：必须发现新的限制或回归失败
   - 从 ❓ 改为 ⛔：必须有业务边界决策
   - 从 ✅ 改为 ❓：必须有明确证据表明该能力失效
7. **内容发布模块有硬边界**：
   - 获取用户提供的文案 / 图片：✅ 可做
   - 发布笔记：⛔ 明确不做
   - 内容生成（文案/图片）：⛔ 明确不做
8. **沉淀优先于进度**：宁可状态保守，也不要把未验证能力标成 ✅。

## 探索优先级建议

下一阶段优先验证以下能力，以形成完整社交互动链路：

1. **`xhs.dm.send` 超时优化** — 发送动作本身成功，但 API 验证阶段（读 UI 层级）超时；需优化验证逻辑或增加超时时间。影响：调用方无法确认消息是否送达
3. **跨设备并发能力** — 已验证：`device.screen` / `size` / `start-apk` / `scroll` / `observe` 三机真并行（wall≈max）；但 Hermes `terminal()` 工具层串行化，需用纯 HTTP 并发验证
4. **私信完整链路** — ✅ 已在 1 号机走通（搜索→用户→主页→私信→发送），可扩展到其他机器
5. **评论回复闭环** — 🔄 `xhs.comment.reply-input` + `xhs.comment.send` 已在 02、04 真机验证；01 上草稿 echo 验证失败（POSTCONDITION_MISS），需 Codex 排查设备差异

## 更新规则

- 每次验证完一项能力，立即更新本文件状态与说明。
- 若验证失败，记录为 🔄 或 ❓，并在 `config/device-control-incidents.json` 中沉淀可复用事件。
- 若业务边界改变，将状态改为 ⛔ 或 🚫，并注明原因。
- 新识别出的能力按模块补充，保持地图完整。
