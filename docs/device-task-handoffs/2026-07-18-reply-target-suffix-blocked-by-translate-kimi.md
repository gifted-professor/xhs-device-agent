# 缺口交接：评论元数据以「翻译」结尾时 reply-input 找不到「回复」

日期：2026-07-18
发现者：kimi（Mac 远程调查 DCI-0056 期间实测）
机器：01（1号机）
优先级：P2

## 问题现象

`xhs.comment.reply-input` 按 DCI-0042 的 **suffix 匹配** 在当前评论面板中定位「回复」按钮。当评论带「翻译」按钮时（多见于含外语/方言的评论），元数据节点文本形如：

```
7分钟前 中国台湾 回复 翻译
```

文本以「翻译」结尾而非「回复」，suffix 匹配恒不命中，命令快速失败：

```
Control 回复 was not found in the fresh UI hierarchy
```

## 实测证据

- 01 号机 yuki 帖子（1 条评论，含日文），元数据为单节点 `7分钟前 中国台湾 回复 翻译`（clickable=false，bounds=[168,769][810,824]）。
- 同一帖子面板上「回复」无法被 reply-input 解析；改用无「翻译」的评论后流程正常。

## 影响能力

- 回复评论：带「翻译」按钮的评论无法作为回复目标；多语言内容场景天然高发。

## 修复方向（建议）

1. 文本内定位：对元数据节点支持「包含 回复」且不与「翻译」混淆的匹配（如匹配 ` 回复` 词边界，或匹配 `回复` 后允许尾随 ` 翻译`）。
2. 或在面板层级中把「回复」「翻译」拆为独立可点击节点（如果 XHS 暴露 span 边界）。
3. 修复前调用方可用 `device.ui` 人工确认目标评论的元数据形态，绕开带「翻译」的评论。

## 验收标准

- [ ] 带「翻译」按钮的评论可被 reply-input 正确解析并打开回复编辑器
- [ ] 无「翻译」的评论回归不退化
